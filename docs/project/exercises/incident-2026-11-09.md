# Trip-wire drill, 9 November 2026

Ran against the Docker lab stack: the regulator on `http://localhost:9100`, the database in the `cyberserious-db-1` container. `TRIP_THRESHOLD` was set to 5 for the run and removed afterwards. The wire reads the threshold at request time.

## Before the burst

One session existed, opened through the group sign-in.

    sessions before: 1

## First burst

Five unauthenticated requests to `/api/v1/me`. The group sign-in counted as the first request in the window, so the warning lands on the fourth call.

    1 401
    2 401
    3 401
    4 429
    5 401

    alerts: SECURITY-TRIP-WARN medium open

The service stays up. The warning answers 429 to that address and writes one medium alert plus one audit row with action `security.trip_warn`.

## Second burst

    sessions before: 1
    1 401
    2 401
    3 401
    4 503
    5 503

    ready: {"ok":true,"locked":true}
    sessions after: 0
    alerts: SECURITY-TRIP high open, SECURITY-TRIP-WARN medium open
    audit: security.trip denied, security.trip_warn denied
    flag file: present

The lock revokes every session, writes the flag file, writes one high alert and one audit row, and answers 503 on every route except `/health/ready`.

## Reopen

Destroy the container and start it again. The flag file lives in the container layer, so a new container starts clean. On the supervised host deployment, remove `data/trip.lock` or start the regulator with `TRIP_OPEN=1`.

## Limits, stated next to the control

- The counter is per client address and per process. A distributed burst does not trip it.
- The warning stage gives an attacker one extra burst. That is the trade for not locking a shared address on the first mistake.
- A shared Docker network allows traffic both ways. The one-way submission rule is configuration, not a bridge rule.
